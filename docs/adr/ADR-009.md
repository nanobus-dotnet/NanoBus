
# ADR-009: Restructure into Four Core NuGet Packages

**Date:** 2026.10.11  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** Solution layout, NuGet publishing  

## Context
Initial NanoBus design had overlapping responsibilities across projects:
- Source generators in separate projects
- Unclear boundaries between public API and internals
- NuGet publishing complicated by interdependencies

## Decision
Restructure into **four core projects**:

| Package | Purpose | Public NuGet? | Dependencies |
|---------|---------|---------------|--------------|
| **NanoBus.Abstractions** | Core interfaces (`IBus`, `IMessage`, `IMessageHandler<T>`, `ITransport`, `IDeadLetterQueue`) | ✓ Yes | None |
| **NanoBus.Core** | Base implementations (`Bus`, `MessageHandlerRegistry`) + core extensions + message handler source generator | ✓ Yes | `NanoBus.Abstractions` |
| **NanoBus.Transports.InMemory** | Production transport + DLQ + extension source generator | ✓ Yes | `NanoBus.Abstractions`, `NanoBus.Core` |
| **NanoBus.Transports.Demo** | Demo/test transport + extension source generation | ✓ Yes | `NanoBus.Abstractions`, `NanoBus.Core` |

## Rationale
- **Clear separation:** Abstractions decoupled from implementations; users building custom transports depend only on abstractions.

- 
- **Simplifies DI:** `services.AddServiceBus()` (from Core) is not exposed; only transport-level setup (`AddInMemoryTransport()`) is public.
- 
- **Scalability:** Future transports (RabbitMQ, Redis, Sql Server, PostgreSql, etc.) can depend on Abstractions only.

## Consequences
- **Positive:**
  - Minimal API surface; users only need to install one transport package `NanoBus.Transports.InMemory` or `NanoBus.Transports.Demo`.
  - Custom transport implementations are straightforward (install `NanoBus.Abstractions` and implement `ITransport`).
  - Each transport exposes its own method to add the service bus to services. `services.AddDemoServiceBus()` and `services.AddInMemoryServiceBus()`
  - Versioning is clear: Abstractions rarely change; transports evolve independently.

- **Negative:**
  - If user messages and/or handlers are in a separate assembly, NanoBusCore NuGet package must be reference for source generation.
  - More projects to maintain and test.
  - Interdependency requires careful testing (integration tests verify Core + Transport together).
  - NanoBusCore NuGet package exposes `services.AddServiceBus(...)` which might be confusing for users since it isn't typically used (but can be).

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Single monolithic package | Couples implementations; breaks custom transports; poor separation of concerns |

## Implementation Notes
- `NanoBus.Core` and transports target `net8.0` (modern, AOT-ready).
- Examples (`DemoConsole`, `DemoWorker`, `InMemoryWorker`) add packages via `.csproj`.
