# ADR-010: Referencing Message Types and Handlers From External Assemblies

**Date:** 2026.10.19  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `NanoBus.Core (NanoBusCore NuGet package)`, `MessageHandlerRegistry`, `InMemoryTransport`, `DemoTransport`  

## Context
API consumers need the capability to reference message types and handlers in different assemblies than the target application. This presents challenges for the structure of NanoBus and packages `NanoBus.Core`, `NanoBus.Transports.InMemory`, and `NanoBus.Transports.Demo`. Previous NanoBus architecture would not allow types in different assemblies to be recognized by source generation and message handlers would not be properly registered.

## Decision
- `NanoBus.Core` must be published as its own NuGet package (`NanoBusCore`) and referenced from the external assembly rather than **ONLY** being a transitive dependency to NanoBus transports. In other words, the API consumer's external assembly must directly install the `NanoBusCore` NuGet package and their target application must reference a transport NuGet package, e.g., `NanoBus.Transports.InMemory`.

## Rationale
For any kind of adoption, NanoBus must support types in other assemblies.

## Consequences
- **Positive:** 
  - Transport projects no longer have to reference the shared link `<Compile Include="..\NanoBus.Core\MessageHandlerExtensionsGenerator.cs" Link="MessageHandlerExtensionsGenerator.cs" />` which was done in order to eliminate duplicate code. Since `NanoBus.Core.csproj` now contains `<IncludeBuildOutput>true</IncludeBuildOutput>`, the transport projects can now reference `MessageHandlerExtensionsGenerator.cs` directly.

- **Negative:** 
  - Unconventional code has to be added to `NanoBus.Core.csproj` in order for source generation to work:   
    ```xml
    <ItemGroup>
	  <None Include="$(OutputPath)NanoBus.Core.dll" Pack="true" PackagePath="analyzers/dotnet/cs" />
    </ItemGroup>
    ```
    Typically source generation does not require this.  

- **Neutral:**
  - [List neutrals.]

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Require API consumer to locate message types and handlers in the target assembly | Unfeasible for the API consumer |
| Separate Core and transport projects from source generation projects | Already decided against in favor of consolidation; burdensome for API consumers since most will use source generation anyway | 


## Implementation Notes
`NanoBus.Core` was already reserved so the package is listed as `NanoBusCore` but keeps the `NanoBus.Core` namespace.
