# 2026.10.02 - Handler Lifetime Strategy (Scoped vs. Singleton)

**Date:** 2026.10.02  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `IMessageHandler<T>`, `InMemoryTransport`, `DemoTransport`

## Context
The service bus library requires a handler injection strategy that works across multiple transport implementations (in-memory and future persistent transports). The core library will define handler registration, while transport projects consume it.

## Decision
Handler registration defaults to Scoped lifetime in the core project.

```csharp
services.AddScoped<TMessageHandler>();
```


## Rationale
- Transport portability: Scoped is safe for both in-memory and persistent transports. Singletons fail with stateful dependencies (DbContext, transactions).
- Safety: Per-message isolation prevents handlers from sharing state across calls.
- Allocation negligible: Scoped overhead is trivial compared to actual handler work.
- Convention: Aligns with ASP.NET Core patterns.

## Consequences
- **Positive:** 
  - Handlers work unchanged across in-memory and future persistent transports.
  - No concurrency or state-sharing bugs by default.
  - Familiar mental model for ASP.NET Core developers.

- **Negative:** 
  - Per-message allocation overhead (minor, but exists).
  - Slightly higher memory pressure in extreme throughput scenarios.

- **Neutral:**
  - Handler authors must understand scoped semantics (standard ASP.NET Core knowledge).
  - Opt-in singleton optimization requires future implementation if needed.

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Singleton | 	Incompatible with persistent transports that require stateful dependencies (DbContext, transactions). |
| Transport-specific registration | Breaks the shared-core design and requires handlers to be rewritten per-transport. |


## Implementation Notes
- If profiling reveals allocation as a bottleneck, add opt-in singleton registration for provably stateless handlers.
