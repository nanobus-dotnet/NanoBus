# ADR-004: DLQ with Exponential Backoff Retry Strategy

**Date:** 2026.10.05  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `InMemoryDeadLetterQueue`, `FailedMessage`, `InMemoryTransport`  

## Context
Message delivery can fail due to handler exceptions, timeouts, or transient errors. The system needs a bounded retry strategy that balances reliability with resource efficiency.

## Decision
Implement **exponential backoff with a 60-second cap** in `InMemoryDeadLetterQueue`:
- First retry: 1s
- Second retry: 2s
- Third retry: 4s
- Fourth retry: 8s
- ... (double each time)
- Cap: 60s
- Permanent DLQ after max deliveries exhausted

Polling interval: **1 second** (check for ready messages every 1s in `ProcessDeadLetterQueueAsync`).

## Rationale
- **Reduces CPU waste:** Exponential backoff prevents hammering the handler repeatedly.
- **Realistic recovery windows:** 1s–60s aligns with typical transient failures (network hiccups, lock contention).
- **Memory safety:** `FailedMessage` records cap retry attempts (configurable; default ~10–20 attempts before discard).

## Consequences
- **Positive:**
  - Transient failures automatically recover without operator intervention.
  - CPU-efficient; no busy-wait polling.
  - Clear audit trail (`DeliveryAttempts`, `LastFailedOn`, `LastError`).
- **Negative:**
  - Persistent failures take up to 60s between retries; not suitable for millisecond-critical systems.
  - DLQ requires explicit `ReprocessDeadLetterQueueAsync` call or background polling.
  - Memory grows if many messages fail simultaneously (bounded by application constraints).
- **Neutral:**
  - Backoff is local to the transport; distributed systems would need a shared DLQ.

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Immediate retry (no backoff) | Wastes CPU; can cascade if handler is resource-starved |
| Discard on failure | Loses data; unacceptable for business logic |
| Circuit breaker (fail-fast) | Reduces availability; requires explicit reset; overly complex for in-process |

## Implementation Notes
- Backoff formula: `nextRetryTime = now + min(2^attempt * 1s, 60s)`
- `FailedMessage` record tracks: `DeliveryAttempts`, `LastFailedOn`, `NextRetryTime`, `LastError`, `InvokerToken`.
- Re-delivery via `ProcessChannelAsync` (same path as initial send).
- Max attempts (e.g., 100) to prevent unbounded memory; discard after max.
