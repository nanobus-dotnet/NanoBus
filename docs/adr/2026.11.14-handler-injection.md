# 2026.11.14 - Handler Injection Per Transport

**Date:** 2026.11.14  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `IMessageHandler<T>`, `InMemoryTransport`

## Context
Previous ADR (2026.10.02 - Handler Lifetime Strategy (Scoped vs. Singleton)), handlers were registered in the core library as scoped, applying uniformly across all transports. This approach trades off transport-specific optimization for simplicity and portability.

As transports are added (in-memory, persistent), each with different performance characteristics and dependency patterns, a one-size-fits-all lifetime becomes limiting. Transport implementations should own their own handler lifecycle decisions.

## Decision
Handler injection and registration moves from the core library to individual transport implementations. 


## Rationale
- Transport optimization: In-memory can use singleton for speed; persistent transports can use scoped for safety with stateful deps.
- Flexibility: Each transport chooses the lifecycle that suits its concurrency model and performance requirements.
- Clear separation: Core defines contracts; transports implement infrastructure.
- No breaking changes to handlers: Handler code remains agnostic to registration strategy.

## Consequences
- **Positive:** 
  - In-memory transport uses singleton registration for minimal allocation overhead.
  - Persistent transports can use scoped or transient as needed without compromise.
  - Transport authors have full control over DI strategy.
  - Core library stays lean and focused on interfaces.

- **Negative:** 
  - Handler registration duplicated across transports.
  - Transport authors must understand and manage handler lifetimes correctly.

- **Neutral:**
  - Requires clear documentation on per-transport registration patterns.

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Keep core registration | 	Prevents per-transport optimization; forces scoped overhead on in-memory. |
