# ADR-001: SendAsync should warn on multiple handlers

**Date:** 2026.10.01  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `IServiceBus`, `ITransport`, `IMessageHandler<T>`, `IMessage`  

## Context
In an event-driven system, a command should be sent to a single receiver that performs the command. After the command succeeds, an event can be published informing one or more subscribers that the event occurred. If there are no conventions in place to prevent the API consumer from registering multiple receivers for a given message being sent, must decide between multiple options to notify API consumer, add configuration, and/or log build warnings

## Decision
API consumers calling `SendAsync( )` to send messages with multiple handlers for the same message type will receive a warning that only the first handler registered will receive the message.

## Rationale
In order to balance API ease-of-use and negating runtime or build-time exceptions and/or warnings, this seems a good compromise. Creating multiple message types such as `ICommand` and `IEvent` in place of or in addition to `IMessage` is overly verbose, adds development complexity, and has a steeper learning curve for API consumers. Not logging anything or sending to all message handlers may not be desirable to API consumers. Higher burden for initial development API release. Configuration may be added later.

## Consequences
- **Positive:** 
  - Messages are always sent regardless of having multiple handlers registered. No exceptions throw when attempting to send.
  - Warnings are logged so issues may be traced and corrected if needed.

- **Negative:** 
  - Messages will still be sent even if multiple handlers are registered to receive them. This is contrary to the standard behavior of event-driven systems.
  - Handler count lookups on every message delivery attempt.
  - Not as verbose and clearly intentional as `ICommand` and `IEvent`.

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Instead of `IMessage` create `ICommand` and `IEvent` types to mark commands and events | Excessive infrastructure and decision logic; overly verbose; scanning for two message types |
| In addition to `IMessage`, create `ICommand` and `IEvent` types to mark commands and events | Same as above except now scanning for three message types; adds high complexity to API |
| Deliver message to all handlers; don't warn | API consumer may not be aware message was delivered to more than one handler |
| Log error instead of warning | No system error actually occurred during processing; semantics issue only |
| Deliver message to first handler registered but don't warn | API consumer may not be aware message wasn't delivered to all handlers  |
| Throw exception if multiple handlers registered for same message type (ex: **NServiceBus**) | High burden for API consumer to handle runtime exception; message would eventually go to DLQ indefinitely |
| Scan for multiple handler registrations message handler code generation and throw build error | Adds complexity to source generation; might be undesirable for API consumer |
| Make runtime options configurable, e.g., no logging, deliver to all handlers (and log warning or error), etc. | Higher complexity for initial development API release; too many options when goal is a small, simple API |
| Scan for multiple handler registrations message handler code generation and log build warning | Adds complexity to source generation; Might cause unexpected build warning for API consumer (considered for future release) |




## Notes
- Consider options for future release: Scan for multiple handler registrations message handler code generation and log build warning; make runtime options configurable, e.g., no logging, deliver to all handlers (and log warning or error), etc.
