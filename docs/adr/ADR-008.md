# ADR-008: At-Least-Once Delivery vs. Exactly-Once

**Date:** 2026.10.05  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `InMemoryTransport`, `InMemoryDeadLetterQueue`, `IMessageHandler<T>`  

## Context
The service bus must guarantee some form of message delivery with two common options:
- At-Least-Once delivery guarantees a message will be delivered to the handler at least once.
- Exactly-Once delivery guarantees a message will be delivered **exactly** once and no more. Example: A payment processor message handler **CANNOT** double charge a payment.

Message delivery is auto-acknowledged assuming no exceptions are throw during message handling. Any exceptions cause the message to be placed in the DLQ.

## Decision
- Use At-Least-Once delivery.
- Handlers are required to be idempotent.
- API consumer must handle any de-duplication logic.

## Rationale
- At-Least-Once delivery only tracks successes and failures of a message. If a message handler fails, InMemoryTransport only knows that the message failed. It doesn't know exactly which handler(s) of the message failed. When a message delivery is retried, all handlers of the message type will be triggered again, not just the handler that failed. As long as message handlers are idempotent, i.e., there are no side effects of a duplicate message delivery, this may be acceptable.
- Exactly-Once delivery requires more complex tracking and de-duplication logic to determine which of any message handlers failed to auto-acknowledge a message was received. This places an undue burden on API consumers that only need at-least-once delivery.

## Consequences
- **Positive:** 
  - Simplified infrastructure of the transport with no per-handler tracking of message delivery.
- **Negative:** 
  - Messages may be delivered more than once to designated handler(s).

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| **Exactly-Once delivery** | Too complex for NanoBus initial launch goals, requires de-duplication and tracking logic |
| Add interface handlers can implement to signify no delivery retries | Too complex for NanoBus initial launch goals, will implement later |
