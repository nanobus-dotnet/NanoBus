# ADR-005: Use ValueTask for PublishAsync / SendAsync

**Date:** 2026.10.05  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `ServiceBus`, `InMemoryTransport`, `IMessageHandler<T>`  

## Context
`PublishAsync` and `SendAsync` are called on every message operation. Allocating a `Task` per call 
introduces GC pressure and latency jitter, especially under high throughput.

## Decision
- Use `ValueTask` for `PublishAsync` and `SendAsync` on `IServiceBus`.
- Use `ValueTask` for `IMessageHandler<T>.HandleAsync`.
- Synchronous handlers (that complete immediately) return a completed `ValueTask` (zero allocation).
- Async paths allocate a `Task` only when necessary (i.e., writing to a bounded channel that blocks).

## Rationale
- **Throughput:** Eliminates allocation hot path for synchronous, short-lived handlers.
- **Latency:** Reduces GC pressure; improves cold startup and AOT scenarios.
- **Modern .NET:** Aligns with System.Threading.Tasks.Extensions (v10.0.12+).

## Consequences
- **Positive:** 
  - Measurable throughput improvement (~1–2% in benchmarks on hot path)
  - Better memory profile for serverless/short-lived processes
  - AOT-friendly
- **Negative:** 
  - Slightly more complex API surface (caller must handle ValueTask unwrapping)
  - Less familiar to developers; requires documentation
- **Neutral:** No breaking change if upstream catches exceptions correctly

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Always use `Task` | Higher allocation cost; contradicts AOT/performance goals |


## Implementation Notes
- Handlers **must not block** on `ValueTask.Result` or `.Wait()`.
- Use `await` in all callers; let the compiler optimize.
