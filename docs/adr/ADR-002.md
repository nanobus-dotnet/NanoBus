# ADR-002: Compile-Time Handler Routing via Source Generation

**Date:** 2026.10.02  
**Status:** Accepted  
**Decider(s):** Wayland Young  
**Affected Components:** `MessageHandlerRegistry`, `MessageHandlerExtensionsGenerator`, `InMemoryTransport`  

## Context
Traditional message bus frameworks (MassTransit, NServiceBus) use reflection at startup to scan assemblies 
and discover message handlers. This adds:
- Startup latency (assembly scanning, type loading)
- Runtime overhead (reflection in hot paths)
- Binary bloat (reflection metadata)
- Incompatible with AOT compilation

NanoBus targets serverless, cloud-native, and AOT scenarios where startup time and binary size matter.

## Decision
Use **C# source generation** to scan assemblies at compile-time and generate handler registration code:

1. **Generator:** `MessageHandlerExtensionsGenerator` (runs during build, `net8.0`)
2. **Output:** Extension method `AddNanoBusHandlers()` on `IServiceCollection`
3. **Registration:** Manual `services.AddNanoBus().AddNanoBusHandlers()` (no reflection)
4. **Scope:** Linked file in both demo and InMemory transports for consistency

## Rationale
- **Zero reflection:** All handler discovery happens at compile-time; production code has no reflection overhead.
- **Fast startup:** No assembly scanning; DI container reads pre-generated code.
- **AOT-compatible:** Source-generated code is statically analyzable; avoids dynamic invocation.
- **Compile-time safety:** Missing handlers are caught at build-time, not runtime.
- **Deterministic:** Generated code is explicit and reproducible; easier to audit.

## Consequences
- **Positive:**
  - Startup time: ~10–50ms savings (no assembly scanning).
  - Binary size: ~5–10% smaller (no reflection metadata).
  - AOT-compatible; cold-start serverless scenarios gain 50–200ms.
  - Debugging: Generated code is readable and straightforward to step through.
- **Negative:**
  - Learning curve: Developers unfamiliar with source generators need education.
  - Build overhead: Generator adds ~500ms–1s to clean builds (negligible on incremental).
  - Custom handler registration: Manual registration still required for edge cases.
- **Neutral:**
  - No impact on runtime throughput (reflection overhead is only at build-time not run-time).

## Alternatives Considered
| Alternative | Why Rejected |
|------------|-------------|
| Reflection scanning (like MassTransit) | Breaks AOT; adds startup latency; harder to debug |
| Manual registration only | Scales poorly; boilerplate-heavy for large projects |

## Implementation Notes
- Generator targets handlers in user assembly: `IMessageHandler<T>` implementations.
- Generated method: `public static IServiceCollection AddMessageHandlersTo(this IServiceCollection services, ITransport transport)`
- Output location: `obj/generated/NanoBus/MessageHandlerExtensionsGenerator/` (standard Roslyn location).
- Incremental generation: Only re-run on `.cs` file changes (not on `.csproj` changes).
- Shared logic: `MessageHandlerExtensionsGenerator.cs` linked from transport projects.
